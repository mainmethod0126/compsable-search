## 문제 정의
### 현재 동작
- 선택 조건 영역(`SelectedConditionBasket`)의 칩 목록(`.cs-selected-condition-list`)은 `flex-wrap` 기반으로만 배치되고 높이 제한/스크롤 규칙이 없다.
- 조건 칩이 많아지면 선택 영역이 계속 확장되어 상세 패널/상위 레이아웃을 밀어내고, 특히 모바일에서 가시 영역을 과도하게 점유할 수 있다.

### 기대 동작
- 칩 개수가 많아져도 선택 조건 영역의 높이는 지정된 상한 내에서 유지되고, 초과분은 내부 스크롤로 탐색 가능해야 한다.
- 개별 삭제/전체 삭제 동작, 기존 선택 상태 동기화, 공개 콜백 계약(`onChange` 등)은 회귀 없이 유지되어야 한다.

### 재현 조건
- `ComposableSearch` 렌더 후 지역/키워드 조건을 반복 추가해 칩 수를 대량으로 만든다. (예: 30~200개)
- 데스크톱/모바일 폭에서 선택 조건 영역 높이 변화, 스크롤 가능 여부, 칩 삭제/전체 삭제 동작을 확인한다.

### 영향 범위
- `src/components/SelectedConditionBasket.tsx` (구조 변경 시)
- `src/components/ComposableSearch.css` (스크롤/높이/overflow 정책)
- `src/components/ComposableSearch.test.tsx` (회귀/상호작용 테스트)
- `src/styleIsolation.test.ts` (스타일 계약 테스트)

## 권장 해결안
- 선택 대안: `B`
- 선택 근거:
  - 선택 영역 스크롤 책임을 컴포넌트 내부에 명확히 고정해 후속 UX 변경(헤더 고정, 보조 안내 문구)에도 유연하다.
  - 기존 `SelectedConditionBasket`의 기능 계약을 건드리지 않고 레이아웃 계층만 분리해 회귀 위험을 관리하기 쉽다.
- 기각한 대안과 사유:
  - `A`: 단기 대응은 가능하지만 구조적 확장성이 낮고 스크롤 영역 의미가 불분명하다.
  - `C`: 문제를 해결하지 못하므로 기각한다.

## 테스트 및 검증 계획
### Unit
- 구조 변경 시 `SelectedConditionBasket` 렌더링에서 칩 key/삭제 버튼 식별자 계약이 유지되는지 점검

### Integration
- 다수 칩 생성 상태에서 개별 삭제/전체 삭제 시나리오가 정상 동작하는지 검증
- region + keyword 혼합 칩 상태에서도 동기화가 깨지지 않는지 검증

### Regression
- 기존 `ComposableSearch.test.tsx`의 칩 관련 케이스(추가/삭제/전체삭제) 전수 통과
- `styleIsolation.test.ts`에 selected 영역 스크롤 규칙 계약 추가/검증

### 필요 시 추가
- 성능: 칩 200개 기준 렌더링/삭제 조작 체감 지연 여부 확인 (PRD NFR-006 대응)
- 접근성: 키보드 포커스로 스크롤 영역 내 삭제 버튼 접근 가능 여부 확인

## 배포 / 롤백 / 운영 관측
### 배포 전략
- UI/CSS 변경 중심 단일 PR로 적용하고, 기존 콜백/상태 로직은 무변경 원칙을 유지한다.

### 롤백 전략
- 트리거: 스크롤 적용 후 칩 삭제 불가, 레이아웃 붕괴, 모바일 조작 불가
- 절차: selected 영역 관련 TSX/CSS 변경 커밋 revert 후 기존 배치 규칙으로 복귀

### 운영 관측
- 핵심 지표: 칩 대량 상태에서 삭제 성공률, 전체 삭제 성공률, UI 깨짐 제보 건수
- 로그/트레이싱 포인트: `onChange` 호출 페이로드 길이, 삭제 이벤트 후 조건 수 변화
- 알람 조건: 칩 삭제 실패 재현, selected 영역 overflow로 인한 클릭 불가 이슈 발생
