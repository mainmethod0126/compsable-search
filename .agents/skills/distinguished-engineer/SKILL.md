# Distinguished Engineer 스킬

## 진입 정책을 적용한다

- 요청을 받으면 목표/범위/완료 조건을 먼저 확인한다.
- 다수 요청이 있으면 영향도와 긴급도를 기준으로 우선순위를 정한다.
- 사용자가 이 스킬을 직접 지정하면 즉시 처리하고, 정보가 부족하면 필요한 전제를 확인한다.

## 다음 워크플로를 수행한다

1. 요청을 해결 가능한 기술 문제로 재정의한다(증상, 기대 동작, 성공 지표).
2. 재현 가능한 최소 사례를 만들고 원인 가설을 2~3개로 압축한다.
3. 코드 경로, 상태 전이, 경계 조건을 확인해 루트 원인을 식별한다.
4. 가장 작은 변경으로 해결 가능한 패치를 설계하고 구현한다.
5. 기능 정확성, 성능, 회귀 위험을 검증하고 증거를 기록한다.
6. 재발 방지를 위한 테스트/가드레일/운영 체크를 남긴다.

다음 파일을 먼저 읽는다:
- `PRD.md`
- `PRD.en.md`
- `package.json`
- 영향 범위가 있는 `src/` 하위 코드
- 관련 테스트 및 설정 파일

필요하면 다음 참조 파일을 읽는다:
- `references/role-definition.md`
- `references/problem-solving-playbook.md`
- `references/engineering-review-rubric.md`

## 해결 원칙을 적용한다

- 빠른 추측보다 재현과 계측을 우선한다.
- 문제 원인을 증상 레벨이 아닌 시스템 레벨로 설명한다.
- 패치는 최소 변경을 우선하되 장기 유지보수성을 훼손하지 않는다.
- 복잡성 증가가 불가피하면 명시적인 근거와 대안을 함께 제시한다.
- 성능 이슈는 변경 전후 수치(시간/메모리/번들 크기)를 비교한다.

## SOLID 원칙 준수를 강제한다

- 단일 책임 원칙(SRP)을 적용해 모듈, 훅, 컴포넌트의 변경 이유를 하나로 유지한다.
- 개방-폐쇄 원칙(OCP)을 적용해 기존 안정 경로 수정보다 확장 지점(전략, 어댑터, 합성)을 우선한다.
- 리스코프 치환 원칙(LSP)을 적용해 하위 타입 치환 시 계약(입력/출력/예외/부작용)을 깨지 않게 유지한다.
- 인터페이스 분리 원칙(ISP)을 적용해 소비자별 최소 인터페이스를 제공하고 불필요한 의존을 분리한다.
- 의존성 역전 원칙(DIP)을 적용해 상위 정책이 구체 구현이 아닌 추상화에 의존하도록 경계를 설계한다.
- 리팩터링 또는 신규 설계 시 SOLID 위반 여부와 예외 허용 근거를 결과에 명시한다.

## 저장소 제약사항을 강제한다

- 공개 React 컴포넌트 라이브러리 배포(npm 기준)를 전제로 판단한다.
- 외부 의존성 추가 시 필요성, 대안, 충돌 위험을 함께 기록한다.
- API는 단순성, 예측 가능성, 하위 호환성을 우선한다.
- 전역 부작용(CSS 누수, 런타임 글로벌 수정, 강제 폴리필)을 피한다.

## 출력 형식을 고정한다

- 결과에 다음 항목을 포함한다:
  - 문제 요약과 루트 원인
  - 변경 전략과 선택 근거
  - 검증 결과(테스트/성능/회귀)
  - 잔여 리스크와 완화안
  - 즉시 시작 가능한 다음 작업(Top 3)

## 결과 체크리스트

- 원인 분석이 재현 가능한가
- 변경이 최소 단위로 유지됐는가
- 검증 근거가 코드/명령 기준으로 제시됐는가
- 장기 유지보수성 관점의 부채가 증가하지 않았는가
- SOLID 원칙 위반 여부를 점검하고 예외 근거를 기록했는가
