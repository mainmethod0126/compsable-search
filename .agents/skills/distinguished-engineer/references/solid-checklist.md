# SOLID 점검 체크리스트

## 사용 방법

1. 변경 대상 모듈을 경계 단위(도메인, 애플리케이션, 인프라)로 나눈다.
2. 각 경계에 대해 SRP/OCP/LSP/ISP/DIP를 순서대로 점검한다.
3. 위반 항목을 `문제`, `영향`, `수정 전략`, `검증 방법` 형식으로 기록한다.
4. 즉시 수정이 어려우면 후속 작업 티켓과 수용 기준을 남긴다.

## SRP

- 클래스/모듈에 변경 이유가 하나인가?
- 비즈니스 규칙과 I/O 코드가 분리되어 있는가?
- 테스트에서 외부 의존 없이 핵심 규칙을 검증할 수 있는가?

주요 냄새:
- 하나의 클래스가 DB, HTTP, 도메인 규칙을 동시에 수행함
- 기능 추가 시 동일 파일의 서로 다른 영역을 계속 수정함

## OCP

- 새 정책/유형 추가가 기존 핵심 로직 수정 없이 가능한가?
- 분기문(`if/switch`) 확장이 반복되는 지점이 추상화되었는가?
- 확장 포인트가 인터페이스 또는 전략으로 노출되어 있는가?

주요 냄새:
- 기능 추가마다 기존 거대 함수의 분기만 증가함
- 플러그인 구조가 없어서 코어를 매번 수정함

## LSP

- 하위 구현이 상위 계약의 의미를 유지하는가?
- 예외/반환/부작용 계약이 타입마다 달라지지 않는가?
- 대체 가능한 구현을 공통 테스트로 검증했는가?

주요 냄새:
- 특정 하위 타입만 특별 처리하는 타입 체크가 필요함
- 하위 구현이 상위 메서드의 기대 조건을 약화/강화함

## ISP

- 클라이언트가 사용하지 않는 메서드를 구현하도록 강제되지 않는가?
- 인터페이스가 역할 기준으로 분리되어 있는가?
- 읽기/쓰기/관리 기능이 과도하게 결합되지 않았는가?

주요 냄새:
- 한 인터페이스가 수십 개 메서드를 포함함
- 구현체에서 다수 메서드가 `NotImplemented` 상태임

## DIP

- 고수준 정책이 구체 구현(DB 드라이버, SDK)에 직접 결합되지 않는가?
- 외부 의존이 추상화(포트/인터페이스) 뒤에 존재하는가?
- 의존성 주입으로 테스트 더블 교체가 쉬운가?

주요 냄새:
- 도메인 레이어에서 프레임워크 API를 직접 호출함
- 생성자 내부에서 구체 구현을 직접 `new` 함
