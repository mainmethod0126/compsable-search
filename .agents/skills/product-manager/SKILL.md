# 제품 매니저 스킬

## 진입 정책을 적용한다

- 요청을 받으면 제품 목표, 범위, 완료 조건을 먼저 확인한다.
- 다수 요청이 있으면 사용자 영향도와 릴리스 긴급도를 기준으로 우선순위를 정한다.
- 사용자가 이 스킬을 직접 지정하면 즉시 처리하고, 정보가 부족하면 필요한 전제를 확인한다.

## 다음 워크플로를 수행한다

1. 요청에서 목표, 대상 사용자, 릴리스 범위를 식별한다.
2. 문서 작성 전에 저장소 컨텍스트를 필요한 범위로만 확인한다.
3. 제약사항을 추출하고 명시적인 PRD 요구사항으로 변환한다.
4. 요청되면 PRD 요구사항을 Epic, Feature, Distinguished-Engineer 작업, Task로 계층 분해한다.
5. 핵심 기능별 기술 구현 경로, 위험 시나리오, 검증 전략을 정의한다.
6. `distinguished-engineer` 지식베이스로 기술 타당성과 품질 리스크를 검증한다.
7. 구현 제안보다 PRD 명세의 완결성과 재현성을 우선한다.
8. 한국어/영어 PRD 문서를 동일한 변경 세트에서 동기화한다.

다음 파일을 먼저 읽는다:
- `AGENTS.md`
- `PRD.md`
- `PRD.en.md`
- `package.json`
- `src/` 하위의 관련 소스 파일

파일이 없거나 비어 있으면 다음 순서로 처리한다:
- `PRD.md`가 없으면 기본 구조(13개 섹션)로 생성한다.
- `PRD.en.md`가 없으면 `PRD.md`와 동일 범위를 영어로 생성한다.
- 둘 중 하나가 비어 있으면 내용이 있는 파일을 기준으로 동기화한다.

필요하면 다음 참조 파일을 읽는다:
- `references/prd-template.md`
- `references/prd-sync-checklist.md`
- `references/prd-breakdown-template.md`
- `../distinguished-engineer/references/role-definition.md`
- `../distinguished-engineer/references/problem-solving-playbook.md`
- `../distinguished-engineer/references/engineering-review-rubric.md`

## 슈퍼개발자 지식베이스를 적용한다

- 핵심 요구사항을 증상/기대 동작/성공 지표로 분해해 문제를 정식화한다.
- 요구사항별로 재현 가능한 검증 경로와 계측 지표를 정의한다.
- 설계 선택지는 `정확성`, `단순성`, `성능`, `안정성`, `확장성` 루브릭으로 평가한다.
- 고위험 기능은 반증 가능한 가설과 최소 비용 검증 실험을 함께 명시한다.
- 패치/리팩터링이 필요한 요구사항은 최소 변경 원칙과 회귀 위험을 함께 기록한다.
- 주요 컴포넌트/API 요구사항에 SOLID 관점 검토를 포함한다.
- 단일 책임 원칙(SRP)에 따라 변경 이유를 분리한다.
- 개방-폐쇄 원칙(OCP)에 따라 확장 지점을 우선 설계한다.
- 리스코프 치환 원칙(LSP)에 따라 타입/계약 호환성을 보장한다.
- 인터페이스 분리 원칙(ISP)에 따라 소비자별 최소 계약을 설계한다.
- 의존성 역전 원칙(DIP)에 따라 정책과 구현의 의존 방향을 분리한다.
- SOLID 예외가 필요한 경우 허용 근거, 대안, 부작용 완화안을 반드시 남긴다.

## 저장소 제약사항을 강제한다

- 제품을 재사용 가능한 공개 React 컴포넌트 라이브러리로 전제한다.
- 요구사항을 npm 배포 가능 상태 기준으로 설계한다.
- 외부 의존성은 최소화하고 의존성 변경 시 근거를 명시한다.
- API는 간결하고 예측 가능하며 도입이 쉬워야 한다.
- 구현 요구사항에는 구체적인 영어 JSDoc 작성을 포함한다.
- 전역 부작용, CSS 누수, 강제 폴리필 등 사용자 환경 충돌 요소를 방지한다.

## PRD를 실행 단위로 세분화한다

- 요청 시 PRD 요구사항을 `Epic -> Feature -> Distinguished-Engineer -> Task` 계층으로 분해한다.
- Epic은 사용자 가치, 비즈니스 목표, 연결 요구사항 ID(`FR-*`, `NFR-*`, `AC-*`)를 포함한다.
- Feature는 사용자 흐름, 컴포넌트/API 영향 범위, 수용 기준 연결을 포함한다.
- Distinguished-Engineer 단위는 고난도 기술 과제만 포함하고 다음 항목을 필수로 기록한다:
  - 루트 원인 가설
  - 설계 대안 비교
  - 품질 기준(`정확성/단순성/성능/안정성/확장성`) 검토
  - SOLID 위반 가능성과 완화안
- Task는 구현 가능한 최소 작업 단위로 쪼개고, 완료 조건(DoD), 검증 명령, 의존성을 포함한다.
- 모든 분해 결과는 상위-하위 추적이 가능해야 하며 고아 Task를 허용하지 않는다.
- 우선순위는 `Must/Should/Could`와 `P0/P1/P2`를 함께 표기한다.

## 산출물 템플릿을 고정한다

- 신규 PRD 초안은 `references/prd-template.md`를 기반으로 작성한다.
- 기존 PRD 업데이트 시 섹션 구조를 유지하고 변경된 항목만 최소 수정한다.
- `PRD.md`와 `PRD.en.md` 동기화 점검은 `references/prd-sync-checklist.md`를 따른다.
- 분해 산출물은 `references/prd-breakdown-template.md`를 기반으로 작성한다.
- 신규 분해 문서는 `.agents/plans/prd-breakdown-<topic>-<yyyymmdd>.md` 형식으로 저장한다.

## 요구사항을 다음 방식으로 작성한다

- 모든 요구사항은 테스트 가능하고 모호하지 않게 작성한다.
- 정성적 표현보다 측정 가능한 표현을 우선한다.
- 우선순위 라벨 `Must`, `Should`, `Could`를 부여한다.
- 요구사항 ID를 사용해 추적 가능하게 관리한다. 권장 형식: `FR-001`, `NFR-001`, `AC-001`.
- 주요 요구사항마다 수용 기준을 연결한다.
- 정보가 부족하면 가정을 명시한다.
- 미결정 사항은 오픈 이슈로 정리한다.
- PRD는 동일한 입력과 제약에서 다른 구현자가 작업해도 동일한 제품으로 수렴할 수준으로 구체화한다.
- 각 핵심 기능마다 사용자 흐름, 상태 변화, 입력/출력, 오류 처리, 예외 케이스, 완료 조건을 포함한다.
- 컴포넌트/API 요구사항에는 props 시그니처, 타입 제약, 기본값, 이벤트 계약, 접근성 요구사항을 명시한다.
- 비기능 요구사항에는 성능/번들 크기/호환성/테스트 범위를 가능한 한 수치 기준으로 명시한다.
- 구현 전략이 있는 요구사항에는 최소 1개의 기술 리스크와 완화안을 연결한다.

## PRD 파일을 동기화한다

- `PRD.md`와 `PRD.en.md`의 섹션 순서와 범위를 일치시킨다.
- 동일한 요구사항 변경은 두 파일에 한 번의 업데이트로 반영한다.
- 한 파일이 비어 있으면 다른 파일 기준으로 초기화한다.
- 두 문서가 동등해질 때까지 번역 공백을 명시적으로 표시한다.

동기화 완료 전에 다음을 검증한다:
- 두 문서의 섹션 제목과 순서가 1:1로 일치한다.
- 요구사항 ID, 우선순위(`Must`/`Should`/`Could`), 수용 기준 매핑이 동일하다.
- 컴포넌트/API 이름, 파라미터, 제약사항이 의미 단위로 동일하다.

## PRD 업데이트 결과 체크리스트

- 변경된 섹션
- 신규 또는 수정된 요구사항
- 추가 또는 수정된 수용 기준
- Epic/Feature/Distinguished-Engineer/Task 분해 결과와 추적 매트릭스
- 기술 루브릭 검토 결과(`정확성/단순성/성능/안정성/확장성`)
- SOLID 위반 여부와 예외 허용 근거
- 제품 의사결정이 필요한 오픈 이슈
- 다음 구현 가능 작업
- 문서 동기화 검증 결과(섹션/요구사항/수용 기준 일치 여부)
- 재현 가능성 검증 결과(해당 PRD만으로 동일 제품 구현 가능 여부와 부족 정보)
