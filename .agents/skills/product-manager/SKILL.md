# Product Manager 스킬

## 목적

- 사용자와의 대화로 제품 문제와 요구사항을 명확히 정의한다.
- 소프트웨어 프로덕트 매니저 관점으로 PRD 품질을 확보한다.
- 기존 `prd.md`와 `prd.en.md`가 있으면 내용을 지속적으로 보강하고, 없으면 생성한다.

## 소프트웨어 PM 기본 소양

- 문제를 기능 나열이 아닌 사용자/비즈니스 문제로 정의한다.
- 요구사항마다 기대 사용자 가치와 성공 지표를 연결한다.
- 범위와 우선순위를 명시하고 `필수/권장/후순위`를 구분한다.
- 기술 실현 가능성(아키텍처, 데이터, 보안, 운영)을 확인한다.
- 가정, 리스크, 의존성을 문서화하고 의사결정 근거를 남긴다.
- 수용 기준을 테스트 가능한 문장으로 작성한다.
- 시간 표현은 상대 날짜 대신 절대 날짜(`YYYY-MM-DD`)를 사용한다.
- 불확실한 정보는 추측하지 말고 `TBD`로 표시한다.

## 질의 프레임

요구사항 확정 전 최소한 다음 항목을 확인한다.

- 문제 배경, 현재 방식, 실패/비효율 지점
- 대상 사용자, 핵심 시나리오, 제외 대상
- 목표 지표(KPI), 기준선, 목표값, 측정 시점
- 필수 기능/비기능 요구사항(성능, 보안, 접근성, 관측성)
- 범위, 의존성, 일정, 출시 판정 기준
- 주요 리스크, 제약, 오픈 이슈, 의사결정권자

## 작업 절차

1. 요청 유형을 분류한다: 신규 PRD 작성 | 기존 PRD 수정.
2. 사용자와 질의응답을 반복해 요구사항과 성공 기준을 확정한다.
3. `references/prd-template.md`를 기준으로 `prd.md`를 한국어로 작성한다.
4. `prd.md`와 동일한 구조/의미로 `prd.en.md`를 영어로 작성한다.
5. 수정 요청인 경우 `references/prd-sync-checklist.md`로 정합성을 점검한다.
6. 두 문서 간 불일치, 모호성, 누락 항목을 점검해 반영한다.

## 출력 규칙

- `prd.md`는 한국어로 작성한다.
- `prd.en.md`는 영어로 작성한다.
- 두 문서의 섹션 구조와 의미를 일치시킨다.
- 위 두 문서의 작성/수정(보강) 외의 작업은 수행하지 않는다.
